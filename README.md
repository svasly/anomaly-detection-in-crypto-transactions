# Anomaly Detection Pipeline in Crypto Transactions

An end-to-end, reproducible anomaly-detection project on **synthetic** cryptocurrency transactions: data simulation, EDA, statistical baselines, unsupervised ML models, SHAP explanations, and a small FastAPI scoring service.

> **Disclaimer:** the business scenario ("UrbanStay Crypto Operations") is hypothetical and all data is synthetic. The metrics illustrate the methodology; they are **not** a claim about performance on real blockchain data.

## Problem

A payment platform that accepts crypto must flag exploit-like transactions (bursts of transfers, large amounts, unusual fees) without flooding analysts with alerts for legitimate large transfers ("whales").

## What the notebook covers

| Step | Content |
|---|---|
| Data | Synthetic ledger of 10,000 transactions: normal traffic, legitimate whales (2%), exploit-like anomalies (1.5%; burst and "low-and-slow" types) |
| EDA | Feature distributions, segment overlap, correlations |
| Baselines | Univariate IQR rule; robust Mahalanobis distance (Minimum Covariance Determinant, no labels) |
| ML models | Isolation Forest (alert-budget threshold), DBSCAN (k-distance plot, `eps` sensitivity) |
| Explainability | SHAP (`TreeExplainer`) on a sample of exploit-like transactions |
| Serving | FastAPI service + Dockerfile, smoke test, latency measurement |

**Evaluation protocol:** stratified 70/30 train/test split; models are fitted without labels, labels are used only for evaluation; Isolation Forest runs with a 2% alert budget (deliberately different from the true 1.5% anomaly rate) and a sensitivity table is reported.

## Results (reference run, test set: 3,000 transactions, 45 anomalies)

| Model | Precision | Recall | False positives |
|---|---|---|---|
| IQR rule | 0.158 | 1.00 | 239 |
| Robust Mahalanobis (MCD) | 0.173 | 1.00 | 215 |
| Isolation Forest | 0.833 | 1.00 | 9 |
| DBSCAN | 0.865 | 1.00 | 7 |

- The statistical baselines flag **all** legitimate whale transfers; Isolation Forest flags about 14% of them.
- DBSCAN is on par with Isolation Forest here, but its quality depends strongly on `eps` and it cannot score new transactions, so Isolation Forest is used for serving.
- KPI check: recall ≥ 95% — met; false-positive reduction vs. IQR ≥ 70% — met (96%); single-request latency ≤ 5 ms — **not met** in the reference run (p95 ≈ 7.6 ms; hardware-dependent, model only, excluding network).
- With only 45 test anomalies and a single seed, small differences between models are within noise.

## Getting started

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
jupyter notebook Anomaly_Detection_Pipeline_in_Crypto_Transactions.ipynb
```

Run all cells (*Kernel → Restart & Run All*). Section 7 creates the model file and the `api/` files. Python 3.10 or newer is recommended.

## Scoring service

The service is provided as a reference implementation. The Docker image and the HTTP layer have **not** been built, deployed or load-tested; only the scoring logic is smoke-tested in the notebook.

Run locally (after executing the notebook):

```bash
cd api
pip install -r requirements.txt
uvicorn main:app --port 8000
```

Or with Docker:

```bash
docker build -t crypto-anomaly-api ./api
docker run -p 8000:8000 crypto-anomaly-api
```

Example request:

```bash
curl -X POST http://localhost:8000/api/v1/score \
  -H "Content-Type: application/json" \
  -d '{"tx_amount_usd": 900.0, "gas_fee_usd": 25.0, "tx_velocity_1h": 22}'
```

Response fields: `anomaly_score` (higher = more anomalous), `anomaly_detected`, and `routing_action` (`APPROVE` or `MANUAL_REVIEW`; transactions are never blocked automatically). Interactive docs are available at `/docs`; a health check at `/health`.

## Limitations

- Synthetic data with simple parametric distributions; real fraud is noisier and less separable.
- Single dataset and seed, no confidence intervals.
- No temporal structure or concept drift; velocity is given as an input rather than computed from a stream.
- The 2% alert budget is an assumption; the cost of a missed exploit versus an unnecessary review is not quantified.

## Next steps

- Validate on a public labelled dataset (e.g., the Elliptic Bitcoin dataset) with time-based splits.
- Repeat experiments over several seeds and report confidence intervals.
- Add drift monitoring, API tests (FastAPI `TestClient`) and a load test.
- Add a simple cost model for alert review versus missed exploits.
